# 2026-09-18 — 가입 동의 화면의 제공자 문구를 세션 값으로 (#156)

> 구현 기준은 캡처된 디자인이다. 기획 문서(`docs/01~07`)는 고치지 않고 갈라지는 지점만 여기 쌓아 둔다.
> 규칙은 [ARCHITECTURE.md](../docs/ARCHITECTURE.md) 「기획 문서와 다르게 구현했다면」.
> 이 화면의 앞선 기록은 `modify/2026-09-14-signup-consent.md` 다 — 이 파일은 #156 이 바꾼 것만 적는다.

---

## 1. 「소셜」 fallback 을 남겼다 — 세션을 봐도 제공자를 모르는 경우가 남는다

- **문서**: `docs/07-screens.md` 화면 목록에 이 화면 자체가 없고(`modify/2026-09-14-signup-consent.md` 1번),
  `docs/05-policy.md` P11 도 「인증 전에는 계정을 만들 수 없다」까지만 정한다. 로그아웃 상태로 가입
  화면 주소를 직접 열었을 때 무엇을 보여 줄지는 어느 문서에도 없다.
- **디자인 · 구현**: 문구의 제공자를 `getViewer().provider` 에서 얻도록 바꿨지만, **「소셜」 fallback 은
  그대로 뒀다.** `src/proxy.ts:30-36` 이 `/signup/*` 를 가드 대상에서 빼고 이 화면에도 자체 가드가 없어서,
  로그아웃 상태로 `/signup/consent` 를 직접 열면 `getViewer()` 가 `null` 이다. 없애려면 로그인 화면으로
  돌려보내야 하는데 그것은 #156 의 금지 범위(인증 흐름 · 리다이렉트 경로 변경)다.
- **고쳐야 할 곳**: 로그아웃 상태의 가입 화면 진입을 막을지 자체가 별도 결정이다. 정하면
  `docs/05-policy.md` P11 과 `docs/07-screens.md` 흐름표에 한 줄 적고, 그때 이 fallback 문장이
  필요한지 다시 본다.

## 2. 같은 제공자를 가입 동의는 「카카오」, 설정은 「Kakao」 로 적는다

- **문서 · 디자인**: 정본 `탄천런.dc.html` 은 세 자리(L105 가입 동의 · L399 설정 내 정보 · L588 탈퇴)가
  모두 같은 `{{ loginProvider }}` 를 쓰고, 그 값은 L1146 에서 **`Kakao` · `Google`** 로 채워진다.
  즉 정본대로면 세 화면이 전부 `Kakao` 다.
- **디자인 · 구현**: 설정 화면은 정본을 따라 `Kakao`(`src/app/settings/profile.ts:19-22`), 가입 동의 화면은
  `카카오`(`src/app/signup/consent/page.tsx`)다. #37 때 한글로 잡힌 뒤 그대로 남았고
  (`modify/2026-09-14-signup-consent.md` 3번), #156 의 완료 조건도 「카카오 계정으로」라서 이 Issue 에서는
  바꾸지 않았다. **문구를 어느 쪽으로 맞출지는 정하지 않은 채로 남아 있다.**
- **고쳐야 할 곳**: 표기를 하나로 정한 뒤 두 파일 중 한쪽을 바꾼다. 문서 쪽 변경은 불필요 —
  `docs/01~07` 은 제공자 표기를 규정하지 않는다.

## 3. 이 화면이 서버 값을 하나 읽게 됐다 — 네 상태 판정의 근거가 바뀐다

- **문서**: `docs/07-screens.md:12` — 모든 화면은 불러오는 중 · 빈 상태 · 오류 · 정상 네 상태를 구분한다.
- **디자인 · 구현**: `modify/2026-09-14-signup-consent.md` 5번은 「원격 데이터도 서버 요청도 없다」를
  근거로 이 화면에 「정상」 하나뿐이라고 적었다. 이제 제공자 이름 때문에 `getViewer()` 를 한 번 읽으므로
  그 근거는 더 이상 맞지 않다. 그래도 **화면에 보이는 상태는 여전히 「정상」 하나다** — server component 가
  기다렸다가 그려서 불러오는 중이 없고, 비어 있을 목록도 없다. 세션이 없으면 1번의 fallback 문구로 그린다.
  세션 조회 자체가 실패하는 경우(DB 장애)는 따로 잡지 않았다. 이 화면에 들어오는 정상 경로가
  `/`(`src/app/page.tsx:22`)와 `src/proxy.ts:50` 인데 **둘 다 같은 조회를 먼저 하므로** 거기서 이미 막히고,
  이 화면만 fallback 으로 살려 두면 고쳐지지 않는 장애를 감추는 셈이 된다.
- **고쳐야 할 곳**: `modify/2026-09-14-signup-consent.md` 5번의 근거 문장(「원격 데이터도 서버 요청도 없다」).
  문서 정리 때 두 기록을 함께 본다.
